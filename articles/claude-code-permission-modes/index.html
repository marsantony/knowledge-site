    Claude Code 權限模式完整指南：從 sandbox 到 bypassPermissions

    重點¶

    • Claude Code 有兩層安全機制：Sandbox（OS 級的檔案/網路隔離）和 Permission Modes（工具呼叫的審批流程），兩者獨立運作
    • 權限模式由寬鬆到嚴格：bypassPermissions > auto > acceptEdits > default（ask before edit）
    • VSCode 右下角預設只顯示 ask before edit、Edit auto、plan mode；要看到 Auto 和 Bypass permissions，需到 VSCode Settings 開啟 "Allow dangerously skip permissions"
    • 預設模式持久化：在 ~/.claude/settings.json 設定 permissions.defaultMode: "acceptEdits" 即可讓每次新對話預設為 Edit automatically（CLI + VSCode 都生效）
    • auto mode 需要 Team plan + Sonnet 4.6 或 Opus 4.6 + 組織 admin 啟用，個人方案目前無法使用
    • bypassPermissions 只適合隔離環境（Container、VM），在一般開發機上使用等於零防線

    背景¶

    在 Claude Code 中頻繁被權限確認打斷工作流程是常見痛點，但不同的解決方案有截然不同的安全取捨。

    Sandbox vs Permission Modes¶

    層級 控制什麼 設定方式
    Sandbox Bash 指令能存取的檔案路徑和網路 domain /sandbox 指令 或 settings.json 的 sandbox 區塊
    Permission Modes 工具呼叫（Edit、Bash、Write 等）是否需要人工確認 VSCode 右下角 mode selector 或 CLI --permission-mode

    兩者獨立：即使開了 bypassPermissions，sandbox 限制仍然生效。

    各模式比較¶

    模式 CLI 參數 行為 適用場景
    Default --permission-mode default 所有工具呼叫都要確認 需要最高安全性
    Accept Edits --permission-mode acceptEdits 檔案編輯自動通過，Bash 仍會問 日常開發（推薦）
    Auto --permission-mode auto 背景分類器判斷安全性，安全操作自動通過 Team plan 用戶想減少打斷
    Bypass --dangerously-skip-permissions 全部跳過，零確認 僅限 Container/VM 等隔離環境

    在 VSCode 啟用進階模式¶

    1. Ctrl+, 開啟 Settings
    2. 搜尋 claudeCode
    3. 開啟 "Allow dangerously skip permissions" toggle
    4. 右下角 mode selector 會多出 Auto 和 Bypass permissions

    --dangerously-skip-permissions 的逐項風險分析¶

    開了之後，所有工具呼叫（包括 dangerouslyDisableSandbox 的 Bash）都會自動放行。以下是各操作類型的實際風險：

    操作類型 風險 說明
    Edit / Write 🟢 低 有 git 可 revert，而且你通常會看 diff
    git push 🟡 中 可能 push 半成品或 force push 覆蓋遠端，solo dev 影響較小但仍難回溯
    GitHub 寫入（gh issue/pr create/merge/close） 🟡 中 可能誤建 issue 或合併未就緒的 PR，但事後可修
    Cloudflare 操作（wrangler deploy/d1/kv） 🔴 高 部署到 production、改資料庫/KV，花錢且難回滾
    Discord Bot 操作 🟡 中 可能啟停 bot 或透過 token 發訊息
    外部網路請求 🟡 中 sandbox 網路限制被繞過，可打任何外部 API

    關鍵洞察：sandbox 管「能不能碰」（OS 級隔離），permission 管「該不該做」（人類審批）。--dangerously-skip-permissions 拿掉的是第二層，而 Claude 又能用 dangerouslyDisableSandbox 繞過第一層——等於兩層都沒了。

    白名單 vs 黑名單策略¶

    想用「全開 + 黑名單攔危險操作」（透過 PreToolUse hook）的做法有根本性問題：

    • 白名單漏掉 → 多按一次確認（小麻煩）
    • 黑名單漏掉 → 直接執行，沒有第二次機會（不可逆）

    黑名單無法窮舉所有危險操作：curl -X POST、python -c "import requests; ..."、新工具出現等都可能繞過關鍵字檢查。

    預設模式持久化¶

    VSCode UI 右下角切換模式只影響當前 session。要讓預設模式跨 session 持久生效，有兩個設定位置：

    設定位置 Key 影響範圍
    ~/.claude/settings.json permissions.defaultMode 全域（CLI + VSCode + Desktop 都吃）
    VSCode Settings (settings.json) claudeCode.initialPermissionMode 僅 VSCode 擴充的新對話

    推薦用全域設定，一次搞定：

    {
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}

    可用的值："default" / "acceptEdits" / "plan" / "auto" / "bypassPermissions"

    實務建議¶

    對個人方案用戶，最佳平衡點是 Accept Edits + autoAllowBashIfSandboxed + PreToolUse hook：

    • Accept Edits：檔案編輯不被打斷（最高頻操作）
    • autoAllowBashIfSandboxed: true：sandbox 內的 Bash 自動通過
    • PreToolUse hook：Read / Glob / Grep / WebSearch / WebFetch 自動放行
    • 結果：日常 90%+ 的操作零確認，只有跨出 sandbox 的危險操作（git push、wrangler deploy、外部 API 呼叫）才需要人工確認

    這個組合的效果等同「全開 + 危險攔截」，但安全方向是白名單（fail-safe）而非黑名單（fail-open）。不需要 --dangerously-skip-permissions。

    PreToolUse Hook 技術格式¶

    Hook 腳本透過 stdin 接收 JSON，輸出 JSON 控制行為：

    # 讀取工具輸入
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | python3 -c "
import sys, json
d = json.load(sys.stdin)
print(d.get('tool_input', {}).get('command', ''))
")

    三種輸出模式：

    行為 做法
    允許（無訊息） exit 0
    Block + 告知 Claude exit 2，stderr 訊息會顯示給 Claude
    允許 + 加入提醒 context exit 0 + stdout 輸出 JSON permissionDecision: "allow" + additionalContext
    Deny + 告知 Claude exit 0 + stdout 輸出 JSON permissionDecision: "deny" + permissionDecisionReason 
    {
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "additionalContext": "提醒訊息，Claude 會看到"
  }
}

    settings.json 設定格式：

    {
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": "/path/to/hook.sh" }]
    }]
  }
}

    常見 Sandbox 調整：工具 cache 路徑¶

    當某個工具頻繁被 sandbox 擋住，通常是因為它的 cache 目錄不在 sandbox 的寫入白名單內。常見案例：

    工具 Cache 路徑 症狀
    uv（Python 套件管理） ~/.cache/uv 每次 uv run 都要確認 dangerouslyDisableSandbox

    解法：在 settings.json 的 sandbox.filesystem.write.allow 加入 cache 路徑：

    "sandbox": {
  "filesystem": {
    "write": {
      "allow": ["~/.cache/uv"]
    }
  }
}

    加入後，該工具的 Bash 指令會走 autoAllowBashIfSandboxed 自動通過，不再跳確認。遇到其他工具的類似問題時，同樣模式處理即可。

    Auto Mode 的安全機制（深入）¶

    Auto mode 不是盲跑，而是「預設放行 + 動態風險攔截」，核心是背景分類器 + 兩層防護：

    分類器本身 - 用 Sonnet 4.6 作為分類器模型 - 關鍵設計：輸入只看「使用者訊息 + Claude 的工具呼叫」，刻意隔離 Claude 的回應內容與先前工具執行結果 - 用意：讓惡意檔案內容、網頁 injection 無法影響分類結果（classifier 看不到那些內容） - 官方坦承無法 100% 安全：意圖模糊或 context 不足時會漏（false negative）；過度謹慎時會導向替代方案而非直接拒絕（false positive）

    兩層防護架構 - 輸入層（Input guardrail）：掃描工具輸出（檔案讀取、網頁抓取、Shell 結果），偵測 injection 跡象（如偽裝指令），加警告標籤給主 agent - 輸出層（Transcript classifier）：每次工具呼叫前評估，檢查三個維度 — 任務範疇偏離、目標信任度、意圖轉變；高風險才回到權限提示

    實務含意 - Auto mode 仍會擋：下載執行程式、敏感資料外傳、production deploy、大量刪除、權限修改 - 與 bypass mode 差別：bypass 是零防線，auto 有智能安全層 - 不是零風險：隔離環境（Container/VM）跑 untrusted 任務仍建議用 bypass + sandbox 組合

    skipAutoPermissionPrompt 與「直接拒絕不彈窗」現象¶

    Auto mode 下有時會遇到：AI 執行某個命令時沒彈 permission 視窗，卻直接收到 "Permission for this action has been denied" 的錯誤訊息。這不是 bug，是 skipAutoPermissionPrompt: true + Auto mode 的組合刻意設計。

    設定位置：

    {
  "permissions": {
    "defaultMode": "auto"
  },
  "sandbox": {
    "enabled": true,
    "autoAllowBashIfSandboxed": true
  },
  "skipAutoPermissionPrompt": true
}

    三個設定互動的結果：

    動作 sandbox 內？ skipAutoPermissionPrompt 影響 結果
    ls / cat 等讀取 ✓ 無影響 自動過
    沒加 dangerouslyDisableSandbox 的外網請求 ✗（sandbox 擋網路） — sandbox 拒
    加 dangerouslyDisableSandbox: true 跑外部動作 ✗ 脫離 sandbox 啟動：不彈視窗 直接拒絕，附 reason 給 Claude 回頭問使用者

    設計意圖：「不要用 UI 彈窗打斷我，讓 AI 在對話裡跟我確認即可」。所以使用者看到的「直接擋掉」其實是 Auto Mode 的 ask-and-wait 機制，被拒絕是觸發器，Claude 下一步該在對話裡問使用者。

    典型踩雷情境：gh gist create 建私密 gist（預設就是 secret，不是 public），搭 dangerouslyDisableSandbox: true 繞過 sandbox 網路限制，會被 Auto mode 的 data-exfiltration 防線（system reminder 規定「post to chat platforms / share internal docs 需要明確授權」）攔下。risk judge 有時會把「建 secret gist」誤判成「建 public gist」給錯誤理由，但結果是擋下——使用者明確授權後才放行。

    解法選項：

    場景 解法
    使用者對話內明確說「授權發 gist」 當輪放行
    重複性操作想免打擾 permissions.allow 加 "Bash(gh gist create:*)"
    不想走 AI 確認、想彈 UI 點擊 把 skipAutoPermissionPrompt 改 false（會被打斷變多）

    為什麼設計成 AI 確認而非 UI 彈窗：Auto Mode 本身的核心訴求就是「少打斷使用者」，持續彈 UI 跟 Auto Mode 精神衝突。改用「被擋的動作附上 reason 塞回 Claude context」這條路，Claude 可以在對話裡用自然語言跟使用者確認，一次說明情境 + 給多個選項（直接跑 / 加 allow rule / 改 skipAutoPermissionPrompt），比 UI 單次 Y/N 資訊量更高。

    Effort Level（思考深度）設定¶

    除了權限模式，effortLevel 控制模型的 reasoning budget，也可持久化：

    {
  "effortLevel": "xhigh"
}
    值 可用模型
    low / medium / high / max Opus 4.6、Sonnet 4.6
    xhigh 僅 Opus 4.7（Opus 4.7 預設就是 xhigh）

    CLI 替代：claude --effort xhigh；環境變數：CLAUDE_CODE_EFFORT_LEVEL=xhigh。

    Opus 4.7 若無特殊需求不用手動設，xhigh 是它的預設。

    📎 源對話：claude --resume f7c4bda8-aece-4285-8641-759515069af7
