    OAuth2 Flow 比較：Client Credentials vs Authorization Code + PKCE

    重點¶

    • Client Credentials Grant：機器對機器，沒有使用者參與，應用程式用自己的 credentials 直接換 token
    • Authorization Code + PKCE：有使用者參與，需要瀏覽器跳轉、consent screen、redirect callback
    • 判斷用哪個的關鍵：有沒有「使用者」需要授權——有就用 Auth Code + PKCE，沒有就用 Client Credentials
    • Client Credentials 更安全的原因不是「秘密比較厲害」，而是：沒有對外 endpoint、短期 token（1 小時過期）、credentials 不經 URL 傳輸
    • Google Service Account 就是 Client Credentials Flow 的實作：本機用 JSON key 自簽 JWT → Google 驗簽 → 回傳短期 access token

    背景¶

    在評估 Gmail Daily Digest 系統的架構時，比較了兩種存取 Google 資源的方式：

    1. GAS Web App + 自訂 token：部署為公開 endpoint，token 放在 URL query parameter 傳輸。問題是有公開攻擊面，且 token 永久有效。
    2. Service Account + Google Sheets API：GAS 內部定時寫 Spreadsheet，Python 用 Service Account 的 credentials 透過 API 讀取。沒有公開 endpoint，token 自動過期。

    這帶出了 OAuth2 不同 flow 的適用場景討論。

    常見混淆：Service Account 交互 ≠ BFF Pattern¶

    • BFF（Backend for Frontend）：存在的理由是瀏覽器不能安全保存 secret，需要中間人代持。例如 Twitch OAuth proxy。
    • Service Account：純後端程式對後端 API，secret 存本機，不需要中間層。
    • 簡單判斷：有瀏覽器/前端 → 可能需要 BFF；純後端對後端 → 直接打。

    OAuth2 四種 Grant Type 速查¶

    Flow 誰參與 場景
    Authorization Code + PKCE 使用者 + 瀏覽器 + 應用程式 使用者登入授權（Twitch、GitHub Login）
    Client Credentials 只有應用程式 機器對機器（Service Account、API 間通訊）
