    Tailworm：Tailscale SSH 以 root 代辦 Unix socket forwarding 的 confused deputy 與 TOCTOU

    重點¶

    • 根因是 confused deputy，競態只是繞過手法：以 root 執行的 tailscaled 替通過 SSH 認證的使用者 dial／bind Unix socket，過程中沒有降權，只靠路徑白名單把關。TOCTOU 競態（檢查完、使用前把路徑換掉）是用來繞過這道白名單的
    • 前提是攻擊者已有立足點：要控制一台已核准的裝置，policy 裡要有 SSH 規則允許連到目標，而且 forwarding 沒關。這是「受 policy 限制範圍的橫向移動」，不是遠端 RCE
    • 影響：SSH 授權就算只給 non-root 帳號，實際上也等於給了 root。攻擊者碰得到 Docker socket、systemd bus、tailscaled 的 localapi，攔截 localapi 還能偷 pre-auth key、註冊惡意節點
    • 已修補：Tailscale v1.104.4（TS-2026-014～017）、headscale 0.29.7。SSH forwarding 的修法是「以通過認證的使用者身分執行 forwarding」。暫時無法升級時，可設 TS_SSH_DISABLE_FORWARDING=1
    • 通用教訓：用路徑字串做檢查（白名單、檢查時解析 symlink）一修再修都會被繞過（TS-2026-004 → TS-2026-014）。正確做法是讓 kernel 以正確的身分做權限判斷：先降權再操作，或用 dirfd 相對操作，在使用當下驗證

    背景¶

    事件經過¶

    • 2026-10，研究員 Erica Windisch（Cyberdione Labs）發表 Tailworm 報告，在 Tailscale 1.104.2 與 headscale 0.29.5 找到 11 項問題，並在實驗室重現
    • 研究員在 Hacker News 表示「有回報但沒有協調」（reported but not coordinated）。Tailscale 的 blog 則說，他們在 10/24（週六）早上收到報告，兩小時後報告就公開了。公開當下沒有修補版本
    • Tailscale 從 10/26 起陸續發布 TS-2026-014～017，修補版本為 v1.104.4，10/28 再發 blog 說明
    • headscale 在 10/30 發布 0.29.7 security release

    為什麼 root daemon 代辦會出事¶

    SSH 可以轉發 Unix socket，不只 TCP port：

    # 把遠端的 docker.sock 拉到本機
ssh -L /tmp/local.sock:/var/run/docker.sock user@server
    OpenSSH Tailscale SSH（1.104.4 之前）
    誰執行 forwarding fork 出子程序，先降成登入的使用者再做 root 權限的 tailscaled 自己做
    誰擋權限 kernel：使用者沒有權限碰那個 socket，就直接回 EACCES 程式自己比對路徑白名單
    白名單被繞過時 還有 kernel 這一層擋著 以 root 身分直接成功

    tailscaled 要建網路介面、改路由，必須是 root。Tailscale SSH 內建在它裡面，所以只要某個功能忘了先降權，policy 裡「只能用 ubuntu 帳號登入」的限制就破功了。

    這類問題叫 confused deputy：有特權的代理人被拿去替沒有特權的人辦事。

    SSH forwarding 的三個問題（TS-2026-014）¶

    # 問題 本質
    1 ssh -L：root 程式替使用者 dial 目標 socket confused deputy
    2 ssh -R：root 程式刪掉既有的 root socket，換上攻擊者的 listener confused deputy，而且能冒充系統服務
    3 檢查時路徑合法，真正執行 unlink、bind、dial 時，kernel 重新解析的路徑已被 rename 換掉 TOCTOU（Time-of-Check to Time-of-Use）競態，用來繞過白名單

    類比：大樓管理員手上有萬用鑰匙（root），你請他幫你開自己的信箱，他只核對你給的門牌號碼。

    • #1：白名單擋不住所有危險路徑，你直接報機房的門牌，他就開了
    • #3：你報的是自己信箱，他核對完正要走過去，你把門牌換成機房的，他照新門牌開門
    • 正確修法：叫管理員用你的鑰匙去開。機房打不開是因為鑰匙不對，跟核對門牌無關

    拿到 root-only socket 等於拿到 root¶

    報告示範的路徑：

    • Docker socket：docker run -v /:/host 直接掛載主機的整個檔案系統
    • systemd private bus：叫 systemd 以 root 啟動任意服務
    • 替換 root 擁有的服務 socket：其他服務以為在跟系統服務說話，實際上連到攻擊者那裡

    從 root 到新增惡意節點¶

    1. 用 #2 加 #3 搶贏競態，把 tailscaled 的 localapi socket 換成攻擊者的 listener
    2. 之後目標機上 root 執行的 tailscale CLI 指令，都會送到攻擊者那裡
    3. 剛好有人執行帶 pre-auth key 的指令（例如 tailscale up --authkey=...），key 就被攔截
    4. 拿這把 key 註冊新機器，以受害者的身分和 tag 加入 tailnet
    5. 有開 Tailnet Lock 的 tailnet，報告說 disable secret 和簽章資料也在傳輸中被攔到（實驗中沒有真的關閉 Tailnet Lock）

    第 3 步要等到時機，不是一拿到 root 就能自動做到。但攻擊者只要能長期潛伏，總會等到。

    同一類漏洞再犯：為什麼路徑檢查補不完¶

    Bulletin 時間 問題 修法
    TS-2026-004 2026-06 SSH Unix socket forwarding 只做字面比對，symlink 可以指到受保護的 socket 檢查時先解析 symlink，再比對白名單
    TS-2026-014 2026-10 檢查完之後用 rename 換路徑，繞過 TS-2026-004 的修補 改以通過認證的使用者身分執行 forwarding

    TS-2026-004 的修法仍然是「檢查時」做的事，檢查和使用之間的時間差沒有消失，所以還是被繞過。同一時期還有 TS-2026-005（serve 的 Unix socket 代理目標沒限 root）、TS-2026-006（用數字 UID 繞過 root 限制）、TS-2026-009（開頭為 - 的使用者名稱可拿到 root），都是 root daemon 替別人做事時權限沒守好。

    Serve 的 #8 也是同一個模式：防護只在載入設定時檢查，之後換成 symlink 就能繞過。TS-2026-016 的修法是每次 dial 都重新驗證。

    處理這類問題的原則：

    做法 說明
    先降權再操作 最根本。讓 kernel 以使用者身分判斷權限，不用自己檢查路徑。報告指出 Dropbear 2025.89 也是這樣修的
    用 dirfd 相對操作 openat() 搭配 O_NOFOLLOW 等旗標，以已開啟的目錄 fd 為基準操作，路徑不會在中途被重新解析
    在使用當下驗證 不要「載入時驗一次、之後一直用」
    避免只靠路徑字串比對 白名單、黑名單、正規化都只是字串層的判斷，跟 kernel 實際解析的結果可能不一致

    4 App connector（conn25） client 可自選目的地，能連到雲端 metadata 或內網 conn25 是尚未釋出的 pre-production 功能，Tailscale 表示早已知道，這也是延後釋出的原因之一。現行穩定版 app connector 不受影響
    5 Tailscale SSH 已認證的 session 可讓 tailscaled 記憶體耗盡 TS-2026-015 修補
    6 headscale、DERP 記憶體耗盡 headscale 0.29.7 security release（release notes 沒有逐項對應）。client 端讀取 DERP 回應的上限隨 Tailscale 1.104.4 一起更新
    7 serve --tcp 轉發到 localapi socket 可拿到遠端管理權 TS-2026-016 修補
    8 Serve 防護檢查 只在載入設定時檢查，可用 symlink 繞過 TS-2026-016 修補
    9 Funnel 權限只由 CLI 檢查 Tailscale：照設計運作，要繞過需要本機管理員權限
    10 TS_SERVE_ALLOW_ALL_INTERFACES 開啟後 serve 暴露到 tunnel 外 Tailscale：照設計運作，是要手動開啟的設定
    11 HTTP/2 serve 同一條連線的 stream 共用 context，權限在不同 mount 之間互相滲透 TS-2026-017 修補

    嚴重性要怎麼看¶

    • 研究員自評最高為 High，沒有 Critical
    • Tailscale 認為「worm」這個名稱不準確，應該說是「受 tailnet policy 限制的橫向移動」，未經認證的攻擊者無法利用
    • 真正的麻煩在於它破壞了細緻 ACL 的承諾：家用實驗室或小團隊常寫「所有成員 → tag:server」這種寬規則，一台筆電被入侵，就能拿到整批伺服器的 root
    • 報告指出 headscale 0.29.5 的 policy 無法關閉 forwarding，自架的人當時比 SaaS 使用者更難緩解

    揭露爭議：CVD 與 full disclosure¶

    模式 做法 例子
    CVD（Coordinated Vulnerability Disclosure） 先私下通知廠商、約定期限，修好或期限到了才公開 Google Project Zero 90 天、CERT/CC 45 天
    Full disclosure 直接公開，防守方和攻擊方同時知道 早年的 Bugtraq、Full-Disclosure 郵件論壇
    這次 有通知，但依 Tailscale 的說法只提前兩小時 效果接近 full disclosure

    支持這種做法的論點：

    • 報告附了大量不需要等廠商的設定層緩解措施，防守方可以馬上動手
    • PoC 沒有公開
    • 同一類問題當年已經修過好幾次，可以拿來主張廠商需要外部壓力

    反對的論點：

    • 兩小時的通知期，對廠商來說跟沒通知差不多。報告細節足以讓有能力的攻擊者自己重現
    • Tailscale 表示他們本來就在跟外部專家審查同一塊
    • headscale 使用者當時無法用 policy 關掉 forwarding，只能在「整個關掉 Tailscale SSH」和「承受風險」之間選

    從時程看，修補在公開後幾天內就推出了。如果有一段短期的禁止公開期（embargo），使用者很可能可以同時拿到報告與修補。

    防禦清單¶

    • [ ] 所有節點升級到 Tailscale v1.104.4 以上。修補在各節點的 tailscaled，只升級 headscale 不夠
    • [ ] 自架的話，headscale 升級到 0.29.7 以上
    • [ ] 暫時無法升級：在 tailscaled 的服務環境變數設 TS_SSH_DISABLE_FORWARDING=1 後重啟。只會關掉 forwarding，保留 SSH shell 登入。依 headscale release notes，舊版 client 也支援這個變數
    • [ ] SSH 規則改成逐一配對（特定來源 → 特定目的地），敏感系統開 check mode
    • [ ] 不需要 Tailscale SSH 的機器就關掉：tailscale set --ssh=false。關之前先確認還有其他連線方式
    • [ ] 檢查有沒有 serve TCP forward 指到 Unix socket，特別是 tailscaled 自己的 socket
    • [ ] 伺服器開啟 node key expiry
    • [ ] 裝置疑似被入侵時，到控制台刪除裝置。重灌不會撤銷已經被複製走的 key。Tailnet Lock 的簽章節點被入侵時，要一併 rotate
